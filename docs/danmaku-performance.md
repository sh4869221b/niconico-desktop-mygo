# 弾幕の比較測定

## NucBox で比較するもの

A は固定ベース `f9cf3c5348aabaa705265b3bbcd90e0ac43c029c` の独自プレーヤー、B は `codex/danmaku-perf-astra` の測定対象コミットの独自プレーヤー、W は B と同じ EXE の公式 WebView。各ソースを別ディレクトリで同じ Go 1.27.3、`GOARCH=amd64`、`CGO_ENABLED=0` でビルドする。各回に使うコミットと EXE の SHA-256 を記録する。

```powershell
go build -mod=readonly -trimpath -ldflags=-H=windowsgui -o NiconicoDesktopMyGo.exe .
Get-FileHash .\NiconicoDesktopMyGo.exe -Algorithm SHA256
```

1. Windows ビルド、GPU ドライバー、WebView2 バージョン、電源モード、リフレッシュレート、DPI、解像度を記録する。各条件はアプリを終了した状態から始め、同じログイン、同じ検索画面を使う。「設定」から対象プレーヤーを選び、同じ動画 ID を検索して動画詳細の「再生」を押す。
2. 同じ動画・言語・コメント表示設定・速度・画質・映像の実画素サイズを使う。WebView の操作バーを隠したときの**動画領域**を基準にサイズを合わせる。解像度・FPS・配信が切り替わった回、バッファリングが起きた回、コメント取得数や映像サイズの一致を確認できない回には注記する。既往の比較に合わせ、密集する 4:3 の `sm9` と 720p の `sm44301514` を使う。各動画の冒頭 0–22 秒を短い比較区間とし、長時間測定は動画時刻 T=30 秒から 90 秒までとする。冒頭では設定を済ませてから 0 秒にシークする。WebView の時計が進み、`sm9` が独自版と同じ配信解像度であることを記録してから比較に含める。
3. 同じ動画を一度読み込み、T の 15 秒前から通常再生して、動画時刻 T から 60 秒を測る。別ウィンドウの重なり、デスクトップ録画、マウス操作などは全条件でそろえる。対象動画を再度開いて各ランを独立させる。順番を A/B/W、B/W/A、W/A/B と入れ替え、最低 3 組を採る。熱や配信の変動がペア差を超える場合は同じ条件で組を追加する。
4. 性能測定とは別の回で画面を採取する。冒頭の 5、15、21 秒、長時間測定の T+5、T+25、T+45 秒と、長文の入場・退場、上下固定の開始・終了を含む時刻を事前に選ぶ。同一映像フレームでコメント本文と個数、位置、色、縁、複数行の位置、動画外のはみ出しを比較する。動画時刻を合わせきれない画像の差は位置誤差に使わない。一時停止中に位置が止まり、前後のシーク、表示切替、再開で必要なコメントだけに戻ることも確認する。幅の狭い窓・4:3 素材・16:9 素材・リサイズ直後を含める。

## 採取と判定

- **CPU とメモリ**。Windows パフォーマンス モニターで 1 秒間隔のデータ コレクターを作り、Process の ID Process、% Processor Time、Working Set - Private、Private Bytes を全インスタンスから同時採取する。プロセス ツリーと PID、開始・終了時刻を保存し、本体、検索・ログイン画面が使う子プロセス、WebView2 の renderer/GPU/utility を含むこのアプリの全子孫を追跡する。各時点で対象 PID の CPU を合計して論理 CPU 数で割り、メモリは各時点の合計を MiB にする。WebView2 を名前だけで一括集計すると他アプリも入る。**合計プライベート ワーキング セット**を主指標とし、コミット量の合計も併記する。異なる時点のプロセス別最大値を足すと誤差になる。
- **GPU**。同じコレクターに GPU Engine の Utilization Percentage を追加し、PID とアダプター、物理エンジン番号で対応づける。同じエンジンを使う対象 PID の値を時点ごとに合計し、3D、Copy、Video Decode を個別に記録する。DWM の値は別欄で採る。同時実行できるエンジンを合算して単一の使用率にしない。
- **提示されたフレーム**。同じバージョンの PresentMon コンソールで、各ランの計測区間を覆う CSV を保存する。例は `PresentMon.exe --timed 70 --terminate_after_timed --track_gpu_video --date_time --output_file B1.csv`。T 到達時の実時刻で 60 秒に切り出す。動画ウィンドウと、W では対応する WebView2 の表示プロセスの PID・スワップチェーンを特定する。別ウィンドウのチェーンや video/overlay の重複をまとめて FPS に換算しない。表示間隔（DisplayedTime）の p50/p95/p99、表示フレーム数÷実測秒、非表示フレーム率、リフレッシュ周期の 1.5 倍を超える間隔の割合を報告する。表示チェーンを特定できない場合は欠測と記し、同条件の外部録画による表示比較を別枠で行う。[PresentMon のオプションと列定義](https://github.com/GameTechDev/PresentMon/blob/main/README-ConsoleApplication.md)
- **集計**。各回の CPU/GPU は平均と p95、各回のメモリは中央値と最大値、さらに各条件の代表値としてラン間中央値と範囲を記す。各組の B−A、B−W を残す。B の合計メモリが同条件の W より低いことを確認する。CPU/GPU の負担移動、表示数の減少、FPS 低下、長いフレームの増加、クリップ・装飾の差があれば個別に記録し、Cloud の数値だけで採用を決めない。

## Cloud で再現する

本ブランチの `native_danmaku_bench_test.go` を A のソースの作業用コピーにも置き、同じ OS・フォント・Go・MyGo で以下を実行する。ベンチマークは 960×540 DIP の弾幕に 25 ms ごとにコメントを投入し、UI の構築・レイアウト・描画命令生成を測る。動画デコード、GPU 提示、常駐メモリは測定範囲外。両バイナリを先にコンパイルしてから交互に計測するとビルドの影響を除ける。

```sh
go test -mod=readonly ./...
go test -run '^TestDanmakuFrameSequence$' -v
GOMAXPROCS=2 go test -run '^$' -bench BenchmarkDanmakuFrame -benchmem -benchtime=512x -count=5
GOMAXPROCS=2 go test -run '^$' -bench BenchmarkDanmakuLanes -benchmem -benchtime=2000000x -count=5
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -mod=readonly -trimpath -ldflags=-H=windowsgui -o NiconicoDesktopMyGo.exe .
```

Moving は反復本文、Unique は全件異なる本文、Long は長文を 3 件に 1 件含む。Paused は同じ時刻に UI を再構築した場合のコスト。Seek は 5 秒と 12 秒を交互に訪れ、ColdSeek は毎回空の弾幕キャッシュと固有の本文でシークする。Gap は表示対象がない区間。画像テストの `scale=` 以降の出力を A/B で比較すると、同時刻のアクティブ数と、100%・150% でラスタライズした画素全体の SHA-256 を照合できる。

## Cloud の実測（2026-11-27）

Linux amd64、AMD EPYC 9V74、Go 1.27.3、MyGo v0.10.0、GOMAXPROCS=2。固定ベースと変更版を交互に各 5 回計測した中央値。通常再生の密集区間では約 154 件が同時にアクティブになる。割当バイトは 1 操作当たりで、プロセスの常駐メモリは NucBox 側で測る。[全試行の CSV](danmaku-cloud-bench.csv)

| 条件 | ベース ms/フレーム | 変更版 ms/フレーム | ベース → 変更版 B/フレーム |
| --- | ---: | ---: | ---: |
| 反復本文を含む再生 | 0.698 | 0.658 | 4,820 → 2,231 |
| 全件異なる本文の再生 | 0.926 | 0.956 | 7,940 → 7,991 |
| 長文混在 | 1.727 | 1.660 | 30,532 → 13,824 |
| 一時停止中の再描画 | 0.571 | 0.564 | 0 → 0 |
| 同じ区間への再シーク | 8.654 | 0.647 | 1,632,549 → 1,408 |
| キャッシュが空で全件異なるシーク | 9.501 | 10.025 | 1,849,132 → 1,873,838 |
| コメントのない区間 | 0.00217 | 0.00111 | 0 → 0 |

混雑時のレーン探索単体は 314.9 → 61.5 ns/件。本文・指定サイズ・固定/スクロールの組ごとに計測済みの幅・高さ・フォントサイズを再利用するため、シークの効果は訪問済み区間で大きい。初回の固有本文だけの区間はキャッシュへの登録も必要になる。ラベルの個別キー、共通スタイルの親への移動、全件の事前索引も試したが、いずれも通常再生の追加改善が安定せず、事前索引は読み込み時の割当も増やした。

両版の画像テストでは、20 状態のピクセルハッシュとアクティブ件数が一致した。Cloud のメモリ内動画によるプレーヤー操作テスト、Go テストと静的チェック、Windows x64 クロスビルドを実施した。Media Foundation の実再生、GPU/DWM、実表示 FPS、WebView と比べた総メモリは NucBox 担当の測定項目。
